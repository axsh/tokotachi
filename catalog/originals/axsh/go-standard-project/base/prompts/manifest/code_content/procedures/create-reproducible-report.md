# 再現手順レポート作成ワークフロー (Reproducible Report)

このワークフローは、仕様書 (`ideas/`) と実装計画 (`plans/`) を元に、実装済みの機能を**人が手で再現できる**チュートリアル形式のレポートにまとめる。
レポートは「どんな操作をすると、どんな処理が動作して、どんな結果が出るのか」を、手順ごとに示す。

レポートの正本の出力先は `prompts/phases/[Phase]/branches/[Branch]/procedures/` である。`ideas/`、`plans/`、`investigations/` と並ぶフォルダである。
ワークフロー定義を置く `prompts/manifest/code_content/procedures/` とは別の場所である。

## 目的

- 動いていることが外から分かりにくい機能を、人が自分の手で確かめられるようにする。
- 人が実行して合否を判定できる、一種のテストケースとして残す。
- 自動テストとは目的が異なる。自動テストは、実装中の回帰を機械が判定するためのものである。このレポートは、人が読んで手順を追い、同じ結果を再現できることを示すためのものである。
- 手順のコマンドがテストの実行であるとき、テスト関数の中に閉じた処理を、レポートの外に残さない。ログの一行がどの処理の証拠か、その確認が何を意図しているかを、レポートだけで読めるようにする。

## 制約事項

> [!CAUTION]
> - ソースコード、テスト、設定ファイル、仕様書 (`ideas/`)、実装計画 (`plans/`) は変更しない。作成・変更してよいのは、このワークフローのレポートと添付ファイルだけである。
> - 手順が期待どおりに動かなくても、コードや設定を直して通してはいけない。実際の結果をそのまま記録し、ユーザーに報告する。
> - `git push` はユーザーが明示したときだけ行う。

### 許可される操作

- ファイルの閲覧・検索と、読み取り系の Git コマンド
- レポートの手順に書くコマンドとブラウザ操作の実行（ビルドスクリプト、生成済みバイナリ、`go run`、サーバの起動と停止など）
- 手順の実行で生じるデータの作成と、リカバリ手順による破棄
- 中間ファイル（採取した出力、下書き）の作成（`tmp/` 以下のみ）
- レポートと添付ファイルの作成（`procedures/` 以下のみ）と、その `git commit`

### 禁止される操作

- 上記以外のファイルの作成・編集・削除
- リポジトリ全体に効く破壊的な操作（`git reset --hard`、`git clean -fdx`、`git checkout -- .`、`git stash` など）。レポートの手順やリカバリにも書かない
- 手順で作っていないデータ、プロセス、コンテナの削除や停止

## 1. ステータスと入力の確認

1.  **ステータスの取得**:
    *   `scripts/utils/show_current_status.sh` を実行し、JSON 出力から `phase`、`branch` を取得する。
    *   連番は `next_procedures_id` を使う。`show_current_status.sh` はブランチ配下の各サブディレクトリ名に対し `next_<dirname>_id` を出力する。`procedures/` が未作成だとキーが無いので、§2 でディレクトリを作ったあと再実行してよい。キーが無い場合は `000` とする。
    *   以下、`[Phase]`、`[Branch]`、`[NextID]` とする。
2.  **入力の特定**:
    *   ユーザーが指定した仕様書・実装計画、または機能を入力とする。指定が無ければ、エディタで開いているファイルを入力とする。
    *   仕様書から実装計画へ辿り、仕様書の要件・検証シナリオと、実装計画の Proposed Changes・Verification Plan を読む。背景の理解に必要なら `investigations/` も読む。
    *   手順で実行するテストがあるときは、そのテスト関数の本体を読む。ログに出る処理と、各判定の意図を、テストのソースから取り出す。
    *   `git log` と実装コードで、対象が実装済みかを確かめる。未実装の部分は手順にせず、その旨を備考に書く。
3.  **確認対象の決定**:
    *   「このレポートで何を確認するか」を一、二文で書けるまで絞る。仕様書の検証シナリオを主な材料にする。
    *   確認対象が互いに独立して複数あるときは、レポートを分けることをユーザーに提案する。

## 2. 出力先の決定

1.  **ディレクトリの確定**:
    *   基本パス: `prompts/phases/[Phase]/branches/[Branch]/procedures/`
    *   例: `prompts/phases/000-foundation/branches/design-thr-first/procedures/`
    *   存在しない場合は作成し、`scripts/utils/show_current_status.sh` を再実行して `next_procedures_id` を確定する。
2.  **ファイル名の決定**:
    *   形式: `[NextID]-[名前].md`（`[NextID]` は 3 桁ゼロ埋め。例: `000`、`001`）
    *   `[名前]` は、確認する振る舞いを表す簡潔な名称にする（例: `Queue-Command-Call`、`Settings-Save-And-Reload`）。
3.  **添付ファイル**:
    *   スクリーンショットなどの添付は、必要なときだけ `procedures/[NextID]-[名前]/` に置く。
    *   レポートからは、レポートファイルからの相対パスで埋め込む（例: `![手順 3 の画面](000-Queue-Command-Call/step-03.png)`）。

## 3. 手順の組み立てと実行

レポートに書く手順は、**エージェント自身が、書くとおりに実行して確かめる**。机上で組み立てた手順だけでレポートを書き終えない。

1.  **初期状態の記録**:
    *   手順を始める前の状態を `tmp/` に記録する。リカバリのあとで、この状態と比べるためである。
    *   例: `git status --short`、待受中のポート、起動中のプロセスやコンテナ、データベースの行数、手順で作る予定のパスの有無。
2.  **通し実行**:
    *   準備、詳細手順、リカバリを、レポートに書く順に、書くとおりのコマンドと画面操作で実行する。作業ディレクトリと環境変数も、レポートに書くものと同じにする。
    *   各手順のコンソール出力、ログ、データベースの状態、画面を `tmp/` に採取する。
    *   期待した処理が本当に動いたことの証拠を探す。画面や標準出力の結果だけでなく、その処理を通ったことを示すログ行、データベースの行、生成されたファイルなどである。
    *   コマンドがテストの実行であるときは、テスト関数が行う準備、呼び出し、差し替え、登録、待ち、判定を、ソースに書かれた順に控える。どの判定がどのログ行の根拠になるかも控える。
    *   既定のログ出力では処理が見えないときは、製品が持つ設定（ログレベルの環境変数など）で見える状態にし、その設定を準備に書く。コードは変えない。
3.  **期待と違うとき**:
    *   実際の結果をそのまま記録する。仕様書・実装計画と実装の食い違いは、備考に書いてユーザーに報告する。
    *   実行できない手順（認証情報、有償のリソース、人の操作が要る画面など）は、実行できない理由を書き、出力は「出力例」として示す。実行していない出力を「実際の出力」と書いてはいけない。
4.  **リカバリの検証**:
    *   リカバリを実行したあと、初期状態の記録と比べ、手順前の状態に戻ったことを確かめる。
    *   戻らない差分があれば、リカバリ手順を直し、通し実行をやり直す。

## 5. 記述ルール

- 読者は、このリポジトリを初めて触る人とする。前提知識を仮定しない。
- チュートリアルとして、手順の順に理解が積み上がるように書く。前の手順の結果を次の手順で使うときは、そのことを書く。
- コマンドは、コピーしてそのまま実行できる形で書く。先頭に `$` などのプロンプトを付けない。出力は別のコードブロックに分ける。
- 各コマンドの作業ディレクトリを示す。
- シェルは bash とする。Windows では Git Bash を使う（`{{policy:project-instructions}}` の「シェル環境の指定」）。
- 実際に実行して採取した出力には「実際の出力」、実行していない出力には「出力例」と書き、区別する。
- 環境で変わる値（ポート、時刻、一時パス、ID、ユーザー名を含む絶対パス）は `<ポート>` のように置き換え、備考で説明する。
- 長いログは、確認に必要な行だけを抜き出す。抜き出しに使ったコマンド（`grep` など）も書く。
- 認証情報、トークン、個人情報は書かない。必要な箇所は `<トークン>` のように伏せる。
- 「期待される処理」と「確認」を対応させる。どのログ行、データベースの行、ファイルが、その処理を通った証拠になるのかを書く。
- 手順のコマンドがテスト、ビルドスクリプト経由のテスト、または `go test` の実行であるときは、**テストの内容**を必ず書く。テストファイルへのパスだけでは足りない。読者がテストを開かなくても、次の三つがレポート内で分かるようにする。
    - テスト関数が、どの順で何をするか。
    - 採取したログの各行が、その中のどの処理を通った証拠か。
    - 各判定が、何を確かめる意図か。
- 「テストを実行した」「PASS した」は、期待される処理でも確認の意図でもない。合格の行は残したうえで、その行がどの処理の結果かを書く。
- ブラウザの操作は、人が画面で見る言葉で書く（画面名、ボタンや入力欄の表示名）。CSS セレクタや自動操作ツールの識別子は書かない。
- サーバなど動き続けるプロセスは、別のターミナルで起動すること、起動できたことの確かめ方、止め方を書く。止める操作はリカバリにも含める。
- 状態を変える準備と手順には、必ずリカバリ項目を対応させる。
- ファイルの参照は `prompts/manifest/code_content/capabilities/portable-file-references.md` に従い、ワークスペースルートからの相対パスで書く。

## 6. セルフレビュー

レポートを保存する前に、以下を確認し、不足があれば直す。

1.  **再現性**: 前提と準備だけを頼りに、別の人が同じ状態を作れるか。作業ディレクトリ、環境変数、ツールのバージョンが書かれているか。
2.  **手順の完全性**: すべての手順に、目的、操作、期待される処理、結果、確認、合格の条件があるか。
3.  **出力の区別**: 実際の出力と出力例が区別されているか。実行していない出力を実際の出力と書いていないか。
4.  **処理と結果の対応**: 表示された結果だけでなく、期待した処理を通ったことの証拠が示されているか。テストを実行する手順では、テストの内容の表が、ログの各行と確認の意図をカバーしているか。テストを開かないと分からない処理が残っていないか。
5.  **リカバリの対応**: 状態を変えた準備と手順のすべてにリカバリ項目があるか。リカバリを実行し、初期状態の記録と一致することを確かめたか。
6.  **安全性**: リカバリに、手順で作っていないものを消す操作や、リポジトリ全体に効く破壊的な操作が無いか。
7.  **追跡性**: 確認する振る舞いが、仕様書の要件・検証シナリオと実装計画に結び付いているか。
8.  **秘匿情報**: 認証情報、トークン、個人の絶対パスが残っていないか。

## 7. 完了確認とコミット

1.  **レポートの Git コミット**:
    *   作成したレポートと添付ファイルだけを `git add` → `git commit` する。
    *   コミットメッセージ例: `docs: add reproducible report XXX-Name`
    ```bash
    git add prompts/phases/[Phase]/branches/[Branch]/procedures/[ファイル名]
    git commit -m 'docs: add reproducible report XXX-Name'
    ```
    *   添付ファイルのディレクトリがある場合は、それも `git add` する。
    *   `git push` はユーザーが明示したときだけ行う。
2.  **レポートの提示**:
    *   作成したファイルを、ワークスペースルートからの相対パスのインラインコードで示す。
    *   確認できたこと、差異があった手順、実行できなかった手順を、チャットでも短く報告する。
3.  **フォローアップ**:
    *   差異の原因を調べる必要があれば `/investigate` を、修正が必要なら `/create-specification` からの開発フローを提案する。勝手に始めない。
    *   実装が変わって手順が古くなったときは、同じレポートを更新するか、新しい `[NextID]` で作り直す。
