# Go 1.27.4 フルアップグレード（脆弱性対応）

## 背景 (Background)

Go 1.27.4（2026-11-10 リリース）はセキュリティ向けポイントリリースであり、cgo・`go` コマンド・コンパイラ・リンカ・`net/http` などの修正を含む（例: CVE-2026-97054）。同時にサポート対象の前メジャー系として Go 1.26.11 も出ているが、本リポジトリは **最新安定系 1.27.4 へフルアップグレード**する。

現状のばらつき:

| 対象 | 現状 |
| :--- | :--- |
| ルート `go.mod`、多数の feature/test モジュール | `go 1.24.0` |
| `features/tt/go.mod` | `go 1.25.0` |
| `catalog/.../go-kotoshiro-mcp-feature/base/go.mod` | `go 1.24.1` + `toolchain go1.24.13` |
| scaffold Dockerfile（kotoshiro） | `golang:1.26-alpine` |
| `features/tt/.devcontainer/Dockerfile` | `golang:1.23-bookworm` |
| README / coding-rules（manifest 源） | Go 1.24+ 表記 |

開発マシン側の toolchain は既に 1.27.4 へ更新済み。リポジトリ内の宣言・コンテナイメージ・文書を揃え、ビルド・統合テストで回帰を確認する。

関連リリース: https://go.dev/doc/devel/release#go1.27.4

---

## 要件 (Requirements)

### 必須要件

#### R1: 追跡対象の全 `go.mod` を Go 1.27.4 系に揃える

次のモジュール（`work/` 配下の worktree コピーは対象外）の `go` ディレクティブを **`go 1.27.4`** に更新する。

- ルート: `go.mod`
- features: `features/tt/go.mod`, `features/release-note/go.mod`, `features/templatizer/go.mod`
- tests: `tests/tt/go.mod`, `tests/release-note/go.mod`
- catalog scaffolds:
  - `catalog/originals/axsh/go-standard-feature/base/go.mod`
  - `catalog/originals/axsh/go-kotoshiro-mcp-feature/base/go.mod`

`toolchain` 行がある場合は **`toolchain go1.27.4`** に更新する。無いモジュールへの新規追加は任意（推奨: セキュリティパッチ固定のため揃えてもよい）。

各モジュールで必要なら `go mod tidy` を実行し、`go.sum` の差分をコミットする。

#### R2: Docker / devcontainer の Go ベースイメージを 1.27.4 系に更新する

| ファイル | 現状 | 目標（例） |
| :--- | :--- | :--- |
| `catalog/originals/axsh/go-kotoshiro-mcp-feature/base/container/Dockerfile` | `golang:1.26-alpine` | `golang:1.27.4-alpine`（または同等の 1.27.4 系 alpine） |
| `features/tt/.devcontainer/Dockerfile` | `golang:1.23-bookworm` | `golang:1.27.4-bookworm`（または同等） |

`features/integration-test/.devcontainer/Dockerfile` は Python ベースのため Go タグ更新は不要。ただし Dockerfile ビルド検証テストは引き続き通ること。

イメージタグは **パッチ固定（1.27.4）を優先**する（脆弱性対応の意図を明示するため）。Docker Hub に当該タグが無い場合のみ `golang:1.27-alpine` / `golang:1.27-bookworm` にフォールバックし、仕様・計画に理由を残す。

#### R3: 現行ドキュメント・ポリシーの最低 Go 版表記を更新する

歴史的な `ideas/`・`plans/` の記述は書き換えない。次の「現行」文書を更新する。

- `README.md`（Go 1.24+ → Go 1.27.4+ または Go 1.27+）
- エージェント coding-rules の源: `prompts/manifest/code_content/policies/coding-rules.md`（`Go (v1.24+)` → `Go (v1.27+)` 相当）
- 現行 scaffold 参照ドキュメント内の `go.mod` 例:
  - `prompts/phases/000-foundation/refs/tokotachi-scaffolds/000-Reference-Manual.md`
  - `prompts/phases/000-foundation/refs/tokotachi-scaffolds/001-HowToExtract.md`

manifest 源を変えた場合、エージェント配下への反映は既存の prompt update 手順に従う（本仕様の実装フェーズで実施可否を計画に明記）。

#### R4: テスト・コメントの整合

- `go 1.24.0` 等を **アサーション期待値**として持つテスト（例: templatizer のフィクスチャ）は、モジュールパス変換のみを検証している場合はそのままでもよい。ただし **実ファイル（scaffold `go.mod`）を読み込むテスト**や、バージョン文字列そのものを検証するテストがあれば 1.27.4 に合わせて更新する。
- `tests/tt/docker_build_test.go` の「Requires golang:1.23+」コメントを現状に合わせて更新する。

#### R5: ビルドと影響範囲の統合テストが通る

- `scripts/process/build.sh` が成功すること。
- Go イメージ変更の影響がある Docker ビルド系統合テストが成功すること（詳細はテスト項目）。

### 任意要件

- 開発者ローカルの二重インストール（`~/sdk/go` と `Program Files\Go`）整理は本仕様の対象外（既に両方 1.27.4）。
- `golang.org/x/*` 等の依存を最新へ上げることは必須としない（`go mod tidy` で自然に動く範囲のみ）。
- catalog の `go-standard-project` 内サンプル文言（例: create-reproducible-report の Go 1.24）は、触れる場合のみ 1.27 系に合わせる（必須ではない）。

### 対象外

- `work/` 配下の worktree コピー
- 過去の ideas/plans の歴史的記述の一括書き換え
- CI 用 `.github/workflows`（本リポジトリに該当ファイルが無い）

## 実現方針 (Implementation Approach)

### バージョン方針

```text
go 1.27.4
toolchain go1.27.4   # 既存 toolchain 行がある／揃える場合
```

- 言語・モジュールの宣言と、実際に使う toolchain パッチを一致させる。
- メジャー飛び（1.24 → 1.27）による破壊的変更があれば、ビルド／テスト失敗箇所を個別修正する（本仕様の完了条件に含む）。

### 変更の順序（推奨）

1. ルートおよび features / tests の `go.mod`（必要なら tidy）
2. catalog scaffold の `go.mod` と Dockerfile
3. `features/tt` の Dockerfile
4. 文書・ポリシー・コメント／テスト期待値
5. `build.sh` → 対象統合テスト

### リスク

- Go 1.25 / 1.26 / 1.27 の言語・標準ライブラリ変更によるコンパイルエラーやテスト失敗
- Docker Hub の `golang:1.27.4-*` タグ欠落（フォールバック手順は R2）
- templatizer / scaffold 抽出ドキュメントと実 `go.mod` のドリフト

## 検証シナリオ (Verification Scenarios)

1. 追跡対象の全 `go.mod` が `go 1.27.4` であり、旧 `toolchain go1.24.13` 等が残っていないこと。
2. kotoshiro / tt の Dockerfile が `golang:1.27.4-...`（または合意したフォールバックタグ）を参照していること。
3. ローカルで `go version` が go1.27.4 であること（開発マシンは済み想定）。
4. `./scripts/process/build.sh` が成功すること。
5. tt の Dockerfile ビルド統合テストが成功すること。
6. README および coding-rules（源）の最低バージョン表記が 1.27 系になっていること。
7. scaffold 参照ドキュメントの `go.mod` 例が実ファイルと一致していること。

## テスト項目 (Testing for the Requirements)

| 要件 | 検証 |
| :--- | :--- |
| R1 / R5 ビルド | `./scripts/process/build.sh` |
| R2 / R5 tt イメージ | `./scripts/process/integration_test.sh --categories "tt" --specify "TestTtDockerfileBuild"` |
| R2 integration-test イメージ（非 Go だが回帰） | `./scripts/process/integration_test.sh --categories "tt" --specify "TestIntegrationTestDockerfileBuild"` |
| R1 release-note モジュール | `./scripts/process/integration_test.sh --categories "release-note"`（go.mod 更新の回帰） |
| R3 文書 | README / coding-rules 源 / scaffold refs の差分レビュー（自動検証は grep で旧 `1.24` 表記が現行パスに残っていないこと） |

### ビルド・全体検証

1. ビルド＋単体テスト:

```bash
./scripts/process/build.sh
```

2. Dockerfile ビルド系（Go イメージ更新の主検証）:

```bash
./scripts/process/integration_test.sh --categories "tt" --specify "TestTtDockerfileBuild|TestIntegrationTestDockerfileBuild"
```

3. release-note カテゴリの回帰:

```bash
./scripts/process/integration_test.sh --categories "release-note"
```

オプションなしの全カテゴリ一括実行は本仕様の必須検証に含めない（Nightly 等に委ねる）。
